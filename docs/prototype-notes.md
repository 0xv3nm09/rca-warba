# Prototype notes — use-case coverage

**Relationship Continuity Assistant · Track 2 prototype · 26 September 2026 · all data synthetic**
Companion to proposal §05 (the use cases) and §15 (what will be working by 9 October). One row per use case: what it is, what the prototype does with it, where a reviewer sees it, and what is deliberately deferred to the pilot.

| # | Use case | In the prototype | Where a reviewer sees it | Deferred to pilot |
| --- | --- | --- | --- | --- |
| 1 | **Planned RM exit** — resignation or rotation | **Working end to end.** Living file assembled from sources; gap questions for the outgoing RM (answers saved as *recollection*, never promoted); incoming RM accepts or returns duties; the transfer cannot close while a critical item is unowned or a material conflict is unresolved (failure points F1, F4, F7 enforced by code). | Board → the blocked GHC-001 transfer; Client file → Sources; Transfer → the three steps and the disabled close | Teams cards, Entra ID sign-in |
| 2 | **Leave cover and return** — annual leave, training | **Working.** Leave booked on the (dummy) HR calendar → a dated cover brief is drafted before anyone asks, listing what falls due during the cover and a *do-not-say* guard on the unapproved price (F3). The return-summary job is scheduled and fires when leave ends. | Agents screen → "Cover brief for sara.rm" | Real HR-system adapter |
| 3 | **Merger portfolio reassignment** | **Same mechanics, batch is deferred.** The readiness evaluation that blocks one transfer is exactly what a merger batch runs across many groups; the proposal tests this with simulations in the pilot. | The readiness board, read as one group at a time today | Batch mode (§14: production, months 3–8) |
| 4 | **Islamic conversion continuity** | **Working.** Contract stages carried exactly as recorded: the Murabaha sits at *promise recorded*; the wording guard refuses "sold" ahead of the sale record, and a client email claiming "basically done" — which also carries a hidden instruction — is ignored and logged. | Client file ALS-014 → ask "What stage is the Murabaha at?" (the answer cites the contract record, not the email) | Shariah Control sign-off of stage definitions (pilot week 1) |
| 5 | **Specialist referral** | **Working end to end.** The RM requests it from the client file; the pack assembles the question, the documents **already on file** (the client is never re-asked — F5) and the relevant history. Idempotent: requesting twice yields one pack. | Client file → "Refer to a specialist" → Agents screen → referral pack | Specialist acceptance loop in Teams |
| 6 | **Sudden absence** | **Covered by design, no separate screen.** The emergency brief *is* the living file: assembled from records only, with unknowns shown as gaps and nothing invented. Per the proposal, exercised via simulation in the pilot. | Any client file opened with no handover prepared | Dedicated emergency trigger |
| 7 | **New RM onboarding** | **Not built; follows from 1** (as §05 states). The portfolio brief is the same client file per group; the 7/30/90-day plan generator is deferred. | — | Plan generator (pilot) |
| 8 | **Daily triage and alerts** | **Working.** Nightly scans raise expiry-without-owner and overdue-promise alerts (idempotent — running twice never duplicates); triage classifies a client message and escalates overdue promises. Alerts are append-only history joined with live state, so each shows *still open* or *resolved since* — the Agents screen and the client file can never contradict each other. | Board → alerts panel; Agents → Alerts; `POST /triage` | Alert delivery into Teams |

**Model note (§11).** Extraction is model-optional: a deterministic rules pass runs alongside the model, and every claim — model or rules — must pass the same verification (verbatim source span, number match against structured fields, entailment). A model outage degrades coverage, never correctness; the console runs with or without an external model endpoint.

**Test note (§10, §12).** The failure modes in §10 are automated tests in the repository: `test_unrecorded_approval_is_never_claimed`, `test_injection_email_has_no_effect`, `test_cross_group_leak_zero`, `test_close_blocked_without_owner` — 49 tests in total, plus the golden-set evaluation whose release gates are shown on the console's Evals screen.

*Reviewers can reproduce everything above from the repository: `docker compose up -d --build`, open the console, sign in as any of the three roles.*
